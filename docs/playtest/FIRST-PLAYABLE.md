# 首轮可玩纵切：先验证想不想再来一局

日期：2026-10-31。状态：**执行方案与空白记录模板，不是已通过的真人验收。**

用户最新方向是：成熟方案按需参考引用，尽量把游戏做出来，验证玩法究竟好不好玩；技术细节可以调整。本轮以此为优先级，不以架构完整、内容数量或自动通关代替玩法验证。

## 1. 只聚焦一段完整体验

- **两位初始修士（近身 / 御剑）、雷泽、快速模式、新账号第一层**。每位至少体验一局；每局用独立测试新档，避免上一局解锁改变比较条件，保留原有个人存档。
- 走完整路径：主菜单 → 选修士 / 洞天 → 移动与遁术 → 击杀拾取 → 顿悟选择 → 调息换装 → 洞主或陨落 → 结算 → 再开一局。
- 不要求首次通关；死亡能进入结算、再开局也属于流程。没体验到洞主就如实记录，不能补注入状态后宣称自然覆盖。
- **不删除、不回退已实现内容**；御兽、其他洞天、传统 / 无尽、高层经济系统留在现有实现中，本轮不以全量打磨作为可试玩的前置条件。
- 先补阻断操作、读不清反馈、成长无感、拖沓战斗；不要为了“更标准”再整体迁移框架。成熟组件只有在明确减少眼前交付成本时才引入，并核对版本与许可。

## 2. 先能玩，再判断好不好玩

### 实机底线（必须由 UE 打包版本确认）

记录提交号、包版本、硬件 / 分辨率 / 画质 / 帧率设置。确认中文字体、窗口缩放、鼠标和键盘焦点、顿悟 / 调息交互、结算与重新开始正常。崩溃、无法继续、重复结算或存档异常一律记技术失败，不能归因于玩家“不懂玩法”。

针对此前 GPU 满载反馈：确认限帧 / 垂直同步实际生效，观察战斗与菜单、前后台切换的帧时间和卡顿；**不以 GPU 利用率一个数字判定性能合格，也不把无渲染运行当作 GPU 验收**。记录使用的目标帧率和实际表现，无法测量则填“未测”。

### 每局只问三件事

1. **哪一次明显变强？** 记时间、所选术法 / 共鸣 / 破境，以及看见或感觉到的改变。没有就写“没有”，不提示玩家应该觉得哪次爽。
2. **如果死亡，原因能解释吗？** 先让玩家自己说；分清“知道危险但没躲开”和“看不见 / 不知道为什么扣血”。胜利则记最危险的一刻。
3. **愿不愿马上再来一局，为什么？** 记原话；自愿继续比被要求完成第二局更有价值，不将这两种情况混算。

首轮成功是：流程确实可玩，并出现可复述的变强体验、可理解的风险，以及自发尝试另一种构筑的理由。失败也有价值：反复没有力量跃迁、死亡难以理解或不想重玩，应先调整核心体验，而非扩充术法数量。两局只是发现问题，**不是总体好评率或平衡达标证明**。

## 3. 用最少实验定位问题

| 观察到的问题 | 下一步只改一个变量 | 怎么判断有没有改善 |
| --- | --- | --- |
| 杀了不少怪仍长时间不升级，波末顿悟扎堆 | 先记录首次顿悟、地上未拾取修为；对照当前自动策略与更积极拾取策略，再由真人确认是否同样发生 | 首次成长更及时且玩家有感；若只是机器人绕路，先修测试策略，不给全局经验加成 |
| 第二波突然暴毙 | 看第一次明显失血时敌种、站位、预警与玩家解释，再单独试一种提示或一种数值调整 | 玩家能提前识别并应对；不能仅凭自动胜率升高就接受调整 |
| 共鸣 / 破境只有数字变大、感觉不明显 | 优先打磨近身、御剑各一条已有成长路线的命中 / 清怪 / 声画反馈 | 玩家不看说明也能指出前后差别；机制定点测试与自然获得记录分开 |
| 洞主太拖、选择界面打断节奏 | 分别测洞主有效输出与空转、读选项时间；一次只试攻击反馈、目标选择或文案中的一项 | 战斗持续有决策而非绕圈等待，选择后能说明获得什么；不要一次改多个系统导致无法归因 |

原设计的快速约 8–12 分钟、洞主约 90–130 秒可作节奏参照，调息停留另记；不是要求每名新手第一次达到的硬门槛。升级是否暂停等规则如需改变，应明确记录为实验，不能悄悄改动再比较。

现有[无界面验证摘要](../architecture/validation/RESULTS.md)和[自然样例](../architecture/validation/natural/results.csv)用于排除崩溃、规则错误并定位节奏问题。固定合法输入、保留失败与观察上限，不挑获胜种子；它们**不证明好玩、真人胜率、画面质量或 UE 实机流畅度**。生产代码或策略改变后须重跑对应证据，旧结果不为新包背书。
