# 完整设计：世界、内容与信息可读性审计

审计基线：`c77483e`；日期：2026-10-30。只读代码审查，不是 UE 编译、运行、视觉、性能或玩家体验验收。此报告不修改玩法代码。

## 立即实施顺序

1. **世界生成 / 异象**：增加以 seed 和洞天 ID 为输入的权威地图快照，模拟与 UE 共用，不让 UE 单独随机视觉。加入中央安全区、圆角闭合边界、连通性校验、外圈障碍/危害/灵脉点/灵兽路线；异象挂灵脉点，并把风险、奖励、预警、已发现状态公开。
2. **完整元素 / 形态 / 内容目录**：扩充金木水火土雷、法体飞剑阵法御兽符箓；实现各形态行为而非只添加名字。由统一可枚举目录驱动 UI、候选池、发现存档、掉落、过滤，移除 12/15/2/5 等散落的固定长度。
3. **数值明示**：术法 1–5 重、完整灵纹说明、敌人/异变/共鸣数值从权威配置出文案；悬停对比升级为双卡全属性，保留现有红升绿降。
4. **完整生态差异**：洞天专属基础/精英/洞主、法宝池、机缘池、环境机制必须实际影响游戏，不接受地图选择按钮换名但仍同一生态。

## 需求级别不能混淆

- **完整设计明确要求**：每次进入重新演化的有限地图；洞天独立生态与专属池；异象可读；六元素五形态；水灭地火且对灼烧目标额外伤害；装备整理便利功能；全部效果与数值明示。
- **内容量建议，而非逐字固定数量合同**：玩法设计“奖励口径与范围边界”将首发 3 洞天、3 修士、30 术法、约 80 法宝明确标为“初版建议，随原型验证调整”；修士章节的 3 位与每位 3 条道统路线也分别是首发建议与后期扩充目标。用户现在要求完整设计时，应以该量级作为待实现内容预算，不应将数字硬要求伪装成已确定验收，也不能用 MVP 完成替代完整功能。
- **仅原型阶段刻意延期，完整游戏仍应实现**：异象、灵石坊市、封存跳过、重铸宝匣劫数、传统/无尽等。配置文档第 0 节明确原型不启用；完整设计的第二/三层是玩家解锁时机，不是永久删除功能的授权。
- **完整首发也刻意延期**：本命法宝每局带出一件（核心爽点验证后再加）、联网与可能的移动端。不应把这三项擅自纳入当前首发阻塞。

## 实施边界与合并风险

- 扩枚举会影响 Stats 的 `elementBonus[2]`、`formBonus[3]`，Resonance 命名字段、Progression 的固定消费数组、存档发现数组以及 UI 的硬编码循环。先统一目录大小和稳定 ID，再扩内容；旧存档需要版本迁移而非直接按新枚举 reinterpret。
- World 与 Simulation 必须共享地图/异象快照；地图重启改变 generation 时重建静态实例，不可只刷新敌人。
- 六异象是设计示例：可以调整具体效果，但不能没有异象系统或只制作不参与战斗的展示项。尤其原配置的灵潮“修为+20%”与完整设计“灵石收益更高”有细化差异，完整实现应明确最终规则且 UI 与实际一致。
- 凡新增功能需纯 C++ 确定性单测和用户流程测试；UE 编译、输入、遮挡、可读性、音效与100+同屏性能均需真实引擎证据。在未跑 UE 时只能声明“源码实现/离线测试通过”，不能声称游戏已完整验收。
